# Managed cloud comparison under 0 CZK/month

**Evaluation date: 2026-10-18. Recommendation only; no accounts, deployment, provisioning or paid features activated.** Quotas are provider documentation facts, not measured Goldberg capacity. Terms may change. A free service can stop; a hard zero-cost budget cannot also guarantee unlimited traffic, storage or uptime.

**Recommend a Supabase Free moderation-only pilot**, contingent on owner acceptance of pausing/restricted service and privacy/retention decisions. It best matches the relational review queue and reduces custom authentication implementation. Expose only small approved catalogue overlays and authenticated contribution/review operations; no practice sync, provider-wide proxy, full encyclopedia mirror, image hosting or Realtime subscriptions by default. If inactivity availability is unacceptable, Workers/D1 is the alternative to prove in a separately authorized security/performance spike; it is not automatically selected as a fallback after provisioning failure. Do not build both backends to postpone a decision.

A static Web Admin can use a free Cloudflare Pages provider subdomain. Free Pages has build/project/file limits; Functions would consume Workers quota and are not “free static requests.” Use no custom paid domain or paid build add-on. [Pages limits](https://developers.cloudflare.com/pages/platform/limits/). Hosting requires owner instruction in a later stage; no web service was created here.

## Zero-cost operating contract

1. Stay on Free organizations/plans and free provider subdomains. Never enable a trial that transitions to billing, paid compute/add-ons, paid queues, SMS, R2 subscription, custom domain or automatic upgrade. Supabase explicitly states no charge on Free; its Pro Spend Cap is **not** a way to meet 0 CZK because Pro itself has a fee. [Cost control](https://supabase.com/docs/guides/platform/cost-control).
2. Verify dashboard plan/organization membership and current terms immediately before any future provisioning. Do not print credentials or activate billing to test limits. Infrastructure provisioning remains outside Stage 1. Keep private deployment credentials outside repo/APK/static assets.
3. Prefer direct provider reads on the device with conservative rate limits and caching. A server proxy would aggregate limits, consume cloud quota and add personal-query processing. Add one only for a documented security/CORS/rate-control need with an explicit cap. Never use a proxy to hide prohibited scraping.
4. Monitor actual API bytes, database/index size, function invocations, active users, error rate and export age. Include dev/test/admin/export traffic. Zero-price quotas do not measure developer time or guarantee free hardware/storage elsewhere. Use existing owner-controlled storage for encrypted off-site exports; no new paid backup service assumed.
5. At internal warning thresholds stop background refresh; at higher thresholds disable contribution intake and nonessential online catalogue fanout, preserving read access where feasible. At provider rejection show offline/unavailable state. Do not delete pending submissions/audit evidence merely to regain quota. Resume only after safe export, reviewed retention and capacity checks. No automated upgrade path.
6. If the provider withdraws Free or terms require payment, disable the optional service, export and prepare a separately reviewed migration; never silently charge or silently collect through another service. Do not generate fake keepalive traffic to evade inactivity policy. No published SLA is promised for this hobby-scale zero-cost deployment.

## Proposed limits and sizing experiment

These are conservative **design targets**, not provider guarantees or measured load capacity. Start with one moderation project, zero binary uploads, 16KiB maximum contribution payload, 20 results/page, 10 pending items/principal, and 5 submissions/day/principal. Owner must validate moderation workload and revise caps before beta. An IP bucket complements account limits but distributed abuse is still possible; allow a global intake kill switch. Do not use a per-process-only limiter as a global security guarantee. Persistent/global quota accounting itself consumes storage/requests.

For Supabase, proposed warning/stop budgets: 250/350MB database, 2.5/3.5GB monthly uncached egress and 250k/350k monthly function invocations, leaving capacity for administration/export/recovery. Managed Auth endpoints still need their own provider abuse limits; a custom gateway does not automatically protect every direct endpoint. Test inability to bypass API intake limits through REST/RPC.

For Workers/D1 alternative, proposed warning/stop budgets: 50k/70k daily Worker requests, 2.5m/3.5m read rows, 50k/70k write rows and 250/350MB per database. Provider quotas may be account-wide and shared with other apps; CPU/latency and D1 index-write amplification must be measured separately. Indexed bounded queries are required; returning 20 rows can still scan millions if unindexed. Some rejected traffic consumes the request budget before application controls run; exhaustion is a service-denial scenario, never justification to pay.

Sizing worksheet: daily active users × calls/day × average measured response bytes × 30, plus admin/auth/export/refresh overhead. Hypothetical **100 users × 10 calls × 10KiB × 30 = 307,200,000 bytes/month**, before overhead; **1,000 users** at the same usage approaches 3.072GB. These are arithmetic examples, not a forecast. A single 20MB bundle downloaded 1,000 times is 20GB, so serving large offline bundles through a 5GB API budget is not viable. Client bundles should assemble small verified provider resources directly; a full hosted bundle service needs a separately proven zero-cost plan.

## Export, recovery and security gates

Propose daily encrypted logical export of moderation data, reviewed mappings and audit revisions to an existing owner-controlled location, with hash verification and a periodic isolated restore. Target RPO ≤24h; RTO is not guaranteed until a drill measures it and owner availability is established. Export jobs and retention must be costed in provider quota; failure disables unsafe publication rather than claiming a valid backup. Do not store exports containing identities in public GitHub releases or Wiki.

Use least-privilege service roles, backend-only secrets, restricted CORS/redirect origins, prepared SQL, explicit role/row checks, bounded fetches, token redaction and security dependency review. Choose processing region and review provider DPA/subprocessors/transfers. Free hosting is not proof of GDPR compliance. Owner-controlled audit retention, moderator access and contributor rights route are unresolved [decisions](STAGES.md). No financial account, OAuth console, region or infrastructure state was changed during this audit.
