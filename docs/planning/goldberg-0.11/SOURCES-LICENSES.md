Primary references are linked beside the claim. Some MusicBrainz documentation opens returned HTTP 429; official indexed documentation was available, but complete field-license classification must be pinned and reviewed in Stage 2 before ingestion. ## Provider traffic and availability

MusicBrainz documents application identification and a ceiling of one request/second, with blocking possible if exceeded; schedule conservatively (one outstanding request, at least one second between starts), honor 503/429 and backoff. Shared NAT/proxy traffic and per-application throttling require additional budgeting; no aggregate availability guarantee. Include a maintained contact URL and real app version in User-Agent. [API identification](https://musicbrainz.org/doc/MusicBrainz_API), [rate policy](https://musicbrainz.org/doc/MusicBrainz_API/Rate_Limiting). Non-commercial API use is not a promise of free commercial services or live feeds: review [MetaBrainz access options](https://metabrainz.org/supporters/account-type) before distribution changes.

Wikimedia's 2026 global limits currently distinguish unidentified requests (10/minute) and a compliant User-Agent class (200/minute); limits can change and may aggregate at client/IP scope. The guidance asks for at most three concurrent requests and honoring Retry-After. Goldberg should start with one concurrent request per provider and a conservative lower local budget; a proxy concentrates traffic and does not increase entitlement. [Current policy](https://www.mediawiki.org/wiki/Wikimedia_APIs/Rate_limits). Action API background work should use maxlag, inspect JSON API errors even with HTTP 200, and defer after overload. [Maxlag](https://www.mediawiki.org/wiki/Manual:Maxlag_parameter), [API usage guidelines](https://foundation.wikimedia.org/wiki/Policy:Wikimedia_Foundation_API_Usage_Guidelines).

All sources: explicit time/response/page limits; HTTPS hosts and redirect revalidation; conditional requests when supported; in-flight coalescing; exponential backoff with jitter, Retry-After as minimum; durable nextAttemptAt for background work; finite retry budget; short negative cache for confirmed missing records only. Never turn transport/parse/rate errors into permanent empty results. Cached reads may continue with timestamp/stale label. Provider failure must not block practice or erase known records. API examples/endpoints and freshness/retention rights require contract fixtures before implementation; no uptime SLA was established.

## Wikipedia endpoint lifecycle

The Action API extract shape above documents the existing client and a possible compatibility fallback, not an unconditional recommendation for new work. [TextExtracts documentation](https://www.mediawiki.org/wiki/Extension:TextExtracts) reports maintenance concerns and points reading clients toward the [Page Content Service](https://www.mediawiki.org/wiki/Page_Content_Service), whose `/api/rest_v1/page/summary/{title}` offers introductory text and page metadata. Stage 2 must verify the current supported endpoint, caching headers and how returned text is tied to a specific revision before selecting it; do not label latest extracts as an immutable article revision merely because a separate revisions request returned an ID. Summary thumbnails still require separate Commons rights validation. Existing app code is unchanged.

## License separation and distribution gate

A composite encyclopedia is a set of independently attributed facts/text/assets. Do not stamp CC0 on the full bundle or derive every field's license from an entity's identity provider. Proposed bundle manifest includes a machine-readable rights record per document/asset and source assertion, plus readable offline credits. CC BY-SA text/media remains separable from CC0 facts; distribution and adaptation obligations still apply. CC BY-NC-SA supplementary MusicBrainz data is excluded by default rather than contaminating a reusable catalogue with uncertain restrictions. Confirm its exact license/version and field boundaries before considering opt-in reuse.

Open Opus's website describes incomplete standardization and historical scraped starting lists; validate field-level accuracy and avoid importing unrelated prose. MusicBrainz coverage and relationships are community-maintained; works, arrangements, releases and recordings are not interchangeable. Wikidata references may disagree and dates have precision; Wikipedia intros can be inaccurate or disputed. Do not auto-merge merely to appear comprehensive. Current name/birth-year matching must not be extended to bands by inventing birth dates.

Album cover art, lyrics, sheet music, score engravings and audio recordings are **not** licensed by a metadata API or a composition's public-domain status. A public-domain score can have a protected edition/scan, and a public-domain composition can have a copyrighted performance. Keep existing external study links; do not scrape Spotify/YouTube/IMSLP/MuseScore content, download recordings or bundle album covers without specific verified rights. Commons presence alone is insufficient; check source-country/distribution-territory issues, personality/trademark restrictions and attribution. Exclude questionable assets and show placeholders/source links.

Stage 2 must capture reviewed documentation revision/date, exact allowed fields, representative payload fixtures, provenance evidence and offline attribution tests for each adapter. This document is an implementation gate, not an opinion that every contemplated use is lawful.
